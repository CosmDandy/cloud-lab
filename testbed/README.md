# VPN testbed

Стендов здесь два, и путать их нельзя — они отвечают на разные вопросы.

| | Стенд оверхеда | Боевой стенд |
|---|---|---|
| Запуск | `bench/run-all.sh` | `bench/prod-matrix.sh` |
| Что меряет | сколько транспорт съедает сам по себе | что реально получает пользователь |
| Сервер | свой xray на той же машине | боевые ноды STO / AMS / OSL |
| Конфиг клиента | из `server-configs/` | из подписки, той же что у людей |
| Трафик | не покидает машину | идёт настоящим путём офис↔нода |
| Источник | `bench/local-origin.py` на localhost | он же, но на самой ноде |

Первый отвечает «стоит ли XHTTP своих накладных расходов». Второй — «почему
вечером тормозит Амстердам». Первый стабилен и воспроизводим, второй зависит
от времени суток и канала, и это не недостаток, а предмет измерения.

## Зачем

Прод-тесты через клиента (Happ) — субъективны: "вроде быстрее" / "вроде латенция выросла". Здесь — точные метрики на одном железе одновременно:

- TCP/TLS handshake time
- DL/UL throughput
- TTFB
- CPU peak per config
- Behavior на connection-freezing-style нагрузке

## Почему источник свой, а не speed.cloudflare.com

11.09.2026 внешний источник перестал годиться: он отвечает `403` на запросы
больше ~26 МБ и `429 Too Many Requests` на серию — лимит идёт по объёму за
окно. Пауза в 5 секунд давала один успех из трёх, после 15 секунд первый же
запрос снова упирался в лимит. Разброс внутри одного варианта доходил до
91 %: сравнивались не транспорты, а везение.

Хуже того, отказ выглядел как успех — curl отрабатывал без ошибки и отдавал
«скорость 9 байт в секунду» на теле в один байт. Теперь код ответа и объём
проверяются наравне со скоростью.

`bench/local-origin.py` эмулирует тот же интерфейс (`/__down?bytes=N`,
`/__up`) и снимает разом и лимит, и капризы внешнего канала. Он же нужен для
upload: зеркала, которые отдают файлы, POST не принимают, а без загрузки не
отличить XHTTP stream-up от packet-up — ради чего они и заводились.

## Архитектура

```
LXC testbed-l-01 (192.168.20.205, VMID 100) на pve-kvt-l-01:
  Docker:
    xray-srv  — одиночный xray-server, поочерёдно меняется конфиг
    xray-cli  — одиночный xray-client → SOCKS5 на localhost:10808
  bench/run-all.sh — главный looper:
    for each server-configs/NN-name/:
      1. Запустить xray-srv с config.json
      2. Сгенерировать client/config.json под текущий transport
      3. Запустить xray-cli (SOCKS5)
      4. Прогнать benchmark.sh через --proxy socks5h://localhost:10808
      5. Сохранить results/<DATE>/NN-name.md
      6. Остановить контейнеры
    Сгенерировать SUMMARY.md
```

Канал офиса — около 400 Мбит/с до Стокгольма и 140 до Амстердама (замер
11.09.2026); тесты прогоняются **последовательно**, иначе они делят его
между собой.

## Боевой стенд

Меряет то, что получает живой пользователь: клиент собирается из **той же
подписки**, что выдана людям, и идёт через реальные инбаунды.

```bash
# 1. Поднять приёмник на нодах — с машины, где есть ssh к проду
bench/origin-deploy.sh up hhh-sto-01 hhh-ams-01 hhh-osl-01

# 2. Прогон — с машины, чьим каналом меряем; ssh к проду ей не нужен
SUB_URL=https://sub.example/<uuid> bench/prod-matrix.sh
SUB_URL=... bench/prod-matrix.sh "HHH-STO"   # только одна нода
PARALLEL=8 SUB_URL=... bench/prod-matrix.sh  # канал, а не транспорт

# 3. Убрать приёмник
bench/origin-deploy.sh down hhh-sto-01 hhh-ams-01 hhh-osl-01
```

Приёмник стоит **на самой ноде**, а не на отдельной машине. Тогда прямой
замер и замер через туннель идут одним путём офис↔нода и сравнимы между
собой, а трафик, который нода шлёт на собственный публичный адрес, ядро
заворачивает локально — внешний канал занимает только туннель, то есть ровно
то, что меряем. Порт 18080 открыт декларативно в
`ansible/inventory/group_vars/vpn_nodes/vars.yaml`, слушателя без прогона там
нет.

Колонка «от канала» в сводке важнее абсолютных мегабит: без знаменателя
медленный протокол неотличим от медленного дня.

### Что здесь легко принять за поломку протокола

- **Офис выходит с двух адресов.** Роутер балансирует каналы и выбирает
  исходящий по назначению, поэтому в списке источников два офисных адреса.
  Пока второго не было, замер до Осло молча не проходил, а выглядело это как
  «нода недоступна».
- **К панели с нестандартных портов не достучаться.** До `hhh-sto-02` из
  офиса доходят только 22, 80 и 443 — SYN на любой другой порт теряется, не
  дойдя до машины. На нодах того же провайдера такого нет. Поэтому приёмник
  и переехал на ноды.
- **`--salamander` и `--hop-ports`** передаются вручную, чтобы отделить
  «протокол сломан» от «подписка не отдала параметр»; см. ниже.

### Поле final_mask в панели

У всех HY2-хостов в таблице `hosts` поле `final_mask` пустое, поэтому
подписка не отдаёт ни salamander-пароль, ни диапазон порт-хоппинга, хотя
серверные инбаунды их задают. Напрашивается вывод, что Salamander и Hop
нерабочие, — и он **неверен**: прогон 11.09.2026 показал 288–294 Мбит/с на
обоих, ноль сбоев, на всех трёх нодах. Клиент подключается и без обфускации.

Вывод, который отсюда следует, скучнее и полезнее: расхождение между
серверным конфигом и содержимым подписки само по себе ничего не доказывает,
пока не измерено. Оверрайды `--salamander` и `--hop-ports` оставлены как раз
чтобы отделять одно от другого.

### Vision и gRPC на Осло

На `hhh-osl-01` инбаунды Vision (2054) и gRPC (2084) не принимают никого:
ноль соединений в access-логе против 21 и 11 на Стокгольме за то же окно.
Порты слушают, Reality отвечает подставным сертификатом, но рукопожатие
клиента не завершается — в логе ноды `REALITY: processed invalid connection`.
Воспроизводится с двух независимых точек (офис и панель в Стокгольме), то
есть дело не в пути из офиса. XHTTP и Hysteria2 на той же ноде работают на
полной скорости.

## Flow для добавления нового inbound в прод

**Stop using "сразу в прод и щупаем Happ"**. Новый паттерн:

1. **Описать** новый inbound (transport+флаги+SNI) — внутри `testbed/server-configs/NN-name/config.json`
2. **Прогнать** `./bench/run-all.sh` (или конкретный конфиг) на LXC
3. **Открыть** `results/<DATE>/NN-name.md` — сравнить с baseline и предыдущими тестами
4. **Решение**: если метрики не хуже baseline и есть прирост — промоут в прод config-profile RemnaWave
5. **После промоута** — повторный тест на прод-ноде (отдельный inbound на тестовом порту), сравнить с testbed

Этот flow зафиксирован в memory как [project_testbed_flow](../../home/vscode/.claude/projects/-workspaces-local-cloud-lab-main/memory/project_testbed_flow.md) — Claude должен следовать ему при любых изменениях inbound параметров.

## Reality keys для testbed

Ключи **не коммитятся** (см. `.gitignore`). Сгенерировать свои и положить в `.env`:

```bash
# приватный + публичный ключ Reality
docker run --rm ghcr.io/xtls/xray-core:latest x25519
# UUID тестового юзера
docker run --rm ghcr.io/xtls/xray-core:latest uuid
```

Затем заполнить `.env` (скопировать из `.env.example`):
```
REALITY_PRIVATE_KEY=<из x25519 PrivateKey>
REALITY_PUBLIC_KEY=<из x25519 Password/PublicKey>
CLIENT_UUID=<из uuid>
```

`generate-configs.py` читает ключ из env. Сгенерированные `server-configs/*/config.json`
и `dist/` содержат ключ → они в `.gitignore`, в репо не попадают.
Это **testbed-only** идентичность, отдельная от прода — не использовать в проде.
