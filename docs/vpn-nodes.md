# Боевые VPN-ноды

Три машины HostHatch, на которых крутится xray и через которые ходят
пользователи. Панель (`hhh-sto-02`) раздаёт им конфиг и собирает статистику;
сами ноды к ней ходить не умеют — направление всегда панель → нода, порт 2222.

| Хост | Адрес | Страна | MTU eth0 |
| --- | --- | --- | --- |
| `hhh-ams-01` | 85.155.190.66 | NL | 1450 |
| `hhh-osl-01` | 91.190.155.237 | NO | 1450 |
| `hhh-sto-01` | 167.104.104.131 | SE | 1500 |

Одинаковые: 1 ядро, 2 ГБ RAM, диск 8.8 ГБ (занято ~40%), Ubuntu с ядром 7.0.0,
xray v26.6.27 в контейнере `remnanode` с `network_mode: host`. Лимит трафика в
панели — 1 ТБ со сбросом 15-го числа.

Разные MTU — не наша настройка, так отдал провайдер. На доступность это не
влияет: проба пакетом 1500 доходит до всех трёх.

## Чем управляются

**Контейнер `remnanode` развёрнут вне репозитория.** Роли, которая его ставит
или обновляет, здесь нет и не планируется — ноды заводились вручную скриптом
Remnawave. Ansible отвечает ровно за одно: тюнинг ядра, роль `vpn_tuning`
через `playbooks/vpn-node-tune.yml`.

Из этого следует практическое: `host_services` у нод не задан намеренно, они не
участвуют в `site.yml`. Прогон без `--limit` их не тронет.

```bash
cd ansible
ansible-playbook -i inventory/cloud.yml playbooks/vpn-node-tune.yml \
  -l hhh-ams-01 --tags sysctl --check --diff
```

Дефолтный инвентарь в `ansible.cfg` — домашний `local.yml`, поэтому
`-i inventory/cloud.yml` обязателен: без него группа `vpn_nodes` не находится и
прогон завершается успехом, не сделав ничего.

Роль разделена на два тега. `sysctl` — безопасная половина, применяется
мгновенно и соединений не рвёт. `limits` дёргает PID 1 через `daemon-reexec` и
**на этих нодах не нужен**: xray живёт в контейнере, и его `nofile` задаёт
docker, а не `pam_limits`. Проверять перед прогоном:

```bash
grep 'Max open files' /proc/$(pgrep -x rw-core)/limits   # уже 1048576
```

Процесс xray в контейнере называется `rw-core`, а не `xray` — `pgrep -x xray`
ничего не найдёт.

## Что дал тюнинг (03.08.2026)

До этого дня роль к нодам не применялась ни разу: руками стоял только BBR в
`/etc/sysctl.d/99-bbr.conf`, всё остальное — дефолты Ubuntu. Симптомы, из-за
которых взялись: простой убивает соединение, канал целиком пропадает, первые
секунды после паузы тормозит.

Значения «до» и что изменилось:

| Параметр | Было | Стало | Зачем |
| --- | --- | --- | --- |
| `net.core.rmem_default` | 212992 | 1048576 | главное. Именно он определяет буфер UDP-сокетов — xray `SO_RCVBUF` явно не ставит. Отсюда `UdpRcvbufErrors` 338 268 на Осло за 19 дней: терялись QUIC и DNS, то есть видео и звонки |
| `tcp_slow_start_after_idle` | 1 | 0 | после каждой паузы больше RTO окно сбрасывалось — «первые секунды тормозит» |
| `tcp_mtu_probing` | 0 | 1 | при MTU 1450 и вырезанном по пути ICMP «Fragmentation needed» соединение с большим MSS зависает молча |
| `ip_local_port_range` | 32768 60999 | 10240 65535 | больше эфемерных портов, но не с 1024 — см. «Инварианты» |
| `netdev_max_backlog` | 1000 | 32768 | против `time_squeeze` 1955 на Осло |
| `somaxconn` | 4096 | 65535 | дефолт десктопа, не прокси |
| `tcp_max_syn_backlog` | 128 | 65535 | то же |
| `nf_conntrack_max` | 65536 | 131072 | запас под `connIdle: 900` в профиле |
| `nf_conntrack_udp_timeout` | 30 / 120 | 60 / 180 | 30 секунд рвали QUIC-сессии на паузах |
| корневой qdisc `eth0` | `pfifo_fast` | `fq` | BBR работал на внутреннем pacing вместо fq |

Про qdisc отдельно, потому что это неочевидно и повторится на любой новой
машине: `net.core.default_qdisc = fq` действует **только на интерфейсы,
поднятые после его установки**. На всех трёх нодах sysctl завели руками на
живой машине, интерфейс уже был поднят — и `eth0` месяц простоял на
`pfifo_fast` при выставленном `fq`. Роль теперь применяет qdisc отдельной
задачей, чтобы не перезагружать боевую ноду.

### Инварианты, которые легко сломать

- **Нижняя граница `ip_local_port_range` выше всех слушателей ноды** (22, 2054,
  2084, 2222, 2444, 2446). С диапазона от 1024 исходящее соединение xray может
  занять порт инбаунда, и следующий перезапуск `remnanode` упадёт на `bind()`
  с `EADDRINUSE` — не каждый раз, а как повезёт. Заведёте слушатель выше
  10240 — поднимайте границу.
- **`nf_conntrack` прописан в `modules-load.d`.** Без этого пять
  conntrack-строк не применяются на загрузке: `systemd-sysctl` идёт после
  `systemd-modules-load`, но модуль на чистой загрузке не грузит никто — его
  подтягивает docker уже потом. На живой машине незаметно, потому что модуль
  давно в памяти. Вместе с `kernel.panic = 10` это значило бы, что после каждой
  тихой автоперезагрузки conntrack-тюнинг молча возвращается к дефолтам.

### Откат

Снимки «до» лежат на каждой ноде: `/root/sysctl-2026-08-03-before.txt` и
`/root/qdisc-2026-08-03-before.txt`.

```bash
rm /etc/sysctl.d/99-vpn-tuning.conf && sysctl --system
tc qdisc replace dev eth0 root pfifo_fast
```

## Конфиг-профиль xray

Профиль живёт **только в постгресе панели** (`config_profiles`, uuid
`2cb12440-8073-45aa-bd46-25cefbc6c46d`, имя `VLESS-Reality`) — в репозитории он
не отражён. Это значит, что после восстановления панели из дампа профиль
приедет вместе с ним, а вот если профиль когда-нибудь пересоздадут с нуля,
описанное ниже потеряется без следа.

### Панель дописывает своё

Конфиг, который реально получает xray, отличается от того, что лежит в
профиле. Панель добавляет `api`, `stats`, инбаунд `REMNAWAVE_API_INBOUND`,
первое правило routing и — важное — свою `policy` со счётчиками:

```json
"policy": {
  "levels": {"0": {"statsUserUplink": true, "statsUserDownlink": true, "statsUserOnline": true}},
  "system": {"statsInboundUplink": true, "statsInboundDownlink": true,
             "statsOutboundUplink": true, "statsOutboundDownlink": true}
}
```

**На этих счётчиках держится учёт трафика пользователей.** Поэтому своя
`policy` в профиле обязана содержать те же поля — иначе при слиянии они могут
пропасть и биллинг перестанет считать.

Посмотреть, что доехало до ноды, можно только с самой ноды: xray читает конфиг
не из файла, а по abstract unix socket от `remnanode`.

```bash
P=$(pgrep -x rw-core | head -1)
ARG=$(tr '\0' '\n' < /proc/$P/cmdline | grep '^@rwint')
SOCK=${ARG%%:*}; SOCK=${SOCK#@}
curl -sS --abstract-unix-socket "$SOCK" "http://localhost${ARG#*:}" | jq '{policy, dns}'
```

### Что добавлено 03.08.2026 и зачем

```json
"policy": {
  "levels": {"0": {"handshake": 8, "connIdle": 900,
                   "statsUserUplink": true, "statsUserDownlink": true, "statsUserOnline": true}},
  "system": {"statsInboundUplink": true, "statsInboundDownlink": true,
             "statsOutboundUplink": true, "statsOutboundDownlink": true}
},
"dns": {"servers": ["1.1.1.1", "8.8.8.8"], "queryStrategy": "UseIPv4"}
```

- `connIdle: 900` вместо дефолтных 300 — пятиминутный простой закрывал
  соединение. Именно это и есть «отошёл, вернулся — всё отвалилось». Заметьте
  взаимодействие с `tcpKeepAliveIdle: 300` в sockopt инбаундов: keepalive
  держит NAT-трансляцию у оператора, но счётчик `connIdle` не сбрасывает — xray
  считает по данным. То есть NAT жив, а xray уже закрыл.
- `handshake: 8` вместо 4 — на канале, который DPI подмораживает на секунды,
  четырёх мало.
- `dns` — до этого xray резолвил через `systemd-resolved` и дальше к резолверу
  провайдера, без своего кеша. При `routing.domainStrategy: IPIfNonMatch` этот
  резолв блокирующий и происходит до передачи данных.
- `queryStrategy: UseIPv4` — глобального IPv6 на нодах нет
  (`ip -6 addr show scope global` пуст). Появится — менять на `UseIP`, иначе
  отрежете IPv6-only ресурсы.
- `uplinkOnly` / `downlinkOnly` намеренно не трогали. Дефолты 2 и 5 секунд тоже
  подозреваются в обрывах длинных загрузок, но что означает значение `0`,
  документация Xray описывает противоречиво: старая формулировка v2ray
  читается как «без ограничения», текущая страница policy — как «закрывать
  быстрее». Пробовать это нужно отдельным шагом на одной ноде, иначе эффект
  неотличим от остального.

## Тиры доступа

Разграничение по серверам сделано 04.08.2026. Главное, что нужно понимать про
модель Remnawave: **сквад даёт доступ к инбаундам, а не к нодам.** Пока все
инбаунды подняты на всех нодах, спрятать от пользователя сервер невозможно —
скрытие хоста из подписки убирает адрес из глаз, но ключ остаётся валидным
везде, где этот инбаунд поднят.

Поэтому у каждой ноды свой набор инбаундов с уникальными тегами — суффикс по
коду ноды. Ключ пользователя физически не попадает в конфиг чужой ноды:

```
VLESS-Vision-AMS, VLESS-gRPC-AMS, VLESS-XHTTP-Stream-AMS,
VLESS-XHTTP-Packet-AMS, VLESS-XHTTP-Packet-443-AMS   → только hhh-ams-01
                            ... то же с -OSL          → только hhh-osl-01
                            ... то же с -STO          → только hhh-sto-01
```

Инбаунды в профиле различаются **только тегом** — порты, ключ Reality, SNI и
пути у одноимённых копий одинаковые. Порты между нодами дублируются, и это
нормально: панель принимает такой профиль, потому что каждый инбаунд назначен
своей ноде.

| Сквад | Ноды | Инбаундов |
| --- | --- | --- |
| `tier-3` | Амстердам (52 мс) | 5 |
| `tier-2` | Амстердам + Осло | 10 |
| `tier-1` | все три | 15 |
| `tier-0` | все три | 15 |

Младшему тиру достался самый дальний сервер намеренно: у него же и запас по
трафику (28 ГБ из 1 ТБ против 241 у Осло), а лучший пинг остаётся стимулом
подняться выше. `tier-0` сейчас совпадает с `tier-1` по правам — он существует
как административный: новые ноды и экспериментальные инбаунды добавляются
только в него.

### Порядок изменения тиров

Тот же, что и для любого нового инбаунда, и шаг со сквадами пропускать нельзя:

1. `PATCH /api/config-profiles` — инбаунд появляется в профиле;
2. `PATCH /api/nodes` — полный список `configProfile.activeInbounds` для ноды;
3. `PATCH /api/internal-squads` — иначе у инбаунда ноль клиентов и панель
   не включает его в конфиг ноды вовсе;
4. `POST`/`PATCH /api/hosts` — что видно в подписке.

Переносить пользователей в новые сквады нужно **до** переключения нод: ключи
попадают на ноду из сквадов, и нода, переключённая раньше, останется без
клиентов.

У пользователя в API **нет `uuid`** — он приходит `null`. Идентификатор для
`PATCH /api/users` — числовой `id`; `GET` работает по `id` или по
`/api/users/by-short-uuid/{shortUuid}`.

### Как править профиль

Через API, токеном со скоупом `*` из `/opt/panel/subscription/.env` на панели.

```bash
UUID=2cb12440-8073-45aa-bd46-25cefbc6c46d
curl -sS -H "Authorization: Bearer $T" \
  "https://vpn.cosmdandy.dev/api/config-profiles/$UUID" | jq '.response.config' > before.json
# правки в after.json, затем:
jq -n --arg uuid "$UUID" --slurpfile cfg after.json '{uuid:$uuid, config:$cfg[0]}' \
  | curl -sS -X PATCH -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
      --data @- "https://vpn.cosmdandy.dev/api/config-profiles"
```

Swagger в проде отключён (`/api/docs-json` отдаёт 404), эндпоинта
`computed-config` нет — он возвращает тот же ресурс, что и обычный GET.

**Форму запроса можно проверить безопасно:** отправить неизменённый конфиг.
Панель разошлёт его нодам, те сравнят хеш, увидят совпадение и xray не тронут —
в логах `remnanode` появится «Xray Core configuration is up-to-date - no restart
required», PID процесса не изменится. Проверено 03.08.2026.

**Настоящее изменение перезапускает xray на всех нодах** — активные сессии
обрываются, клиенты переподключаются сами. Делать в тихое время, одним PATCH,
а не несколькими.
