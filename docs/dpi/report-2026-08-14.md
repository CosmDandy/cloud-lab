### 1.2.6b Третье объяснение: клиента помечают на время

Указание владельца (15.08.2026) и находка агента в habr 1003852 (май 2026)
сходятся: существует механика, при которой клиент после срабатывания
**помечается и держится ограниченным N минут**. В habr описана динамическая
блокировка 47 AS — обращение к триггерному адресу включает ограничение
хостинг-провайдера на **10 минут и только для вашего IP**. В habr 1044396 —
заморозка 120 с, причём «длинный» штрафбан на 600 с автор снял правкой
16.06.

Отдельно владелец указывает на эпизодичность самого DPI: бывают периоды
предельной нагрузки, когда блокируется почти всё, и периоды, когда системы
не справляются и закрытое становится доступным.

**Методическое следствие, важное для всех наших замеров.** Если метка живёт
10–15 минут, то ряды с паузами 45 с и 200 с целиком укладываются внутрь
одного окна — они меряют не «состояние сети», а «состояние нашей метки».
Это делает недействительным сравнение серий, разнесённых на минуты, и
объясняет расхождение T2 / T8 без всякой гипотезы о фазах.

Корректный дизайн: паузы **20+ минут** между сериями, либо разные исходные

### 1.2.11 Hysteria2 снимает заморозку по параллельности

Малина (домашний канал), клиент Hysteria 2.12.1 armv5 → `hhh-ams-01`,
15.08.2026. Два замера подряд, один и тот же URL. `[измерено]`

```
4 параллельных НАПРЯМУЮ        прошло 0/4
4 параллельных ЧЕРЕЗ туннель   прошло 4/4
```

Это самый практичный результат из всех. Заморозка считает **параллельные
TLS-хендшейки к одному SNI**; внутри Hysteria2 весь трафик идёт одним
QUIC-соединением к одному адресу, и считать цензору нечего. Порог, который
на прямом канале срабатывает стабильно (четыре раунда с паузой 200 с — все
`0/4`), через туннель не воспроизводится вовсе.

То есть «работает через раз» в браузере — та самая заморозка от параллельных
запросов страницы к одному домену — туннелем лечится полностью.

**Клиент под armv6 существует:** сборка `hysteria-linux-armv5` запускается на
малине (`ARMv6-compatible processor rev 7`) и держит соединение.

### 1.2.15 ПОПРАВКА: замеры на 2 МБ были артефактом, реальные цифры втрое выше

Все скорости выше сняты на файле 2 МБ. На скорости в несколько МБ/с он
качается меньше секунды — то есть меряется **разгон TCP-окна, а не
установившийся режим**. Повтор на 50 МБ с очищенного сервера. `[измерено]`

| Офис (AS8636) → Амстердам, 50 МБ | Скорость |
|---|---|
| напрямую, TCP/TLS | **27.15 МБ/с = 217 Мбит/с** |
| через Hysteria2 | **25.27 МБ/с = 202 Мбит/с** |
| накладные расходы туннеля | **7%** |

Прежняя цифра «3.69 МБ/с напрямую» занижена в семь раз и в отчёте оставлена
только как иллюстрация того, как ошибается короткий замер. Прежняя оценка
накладных расходов (15%) тоже завышена вдвое.

**Это снимает вопрос «почему на AmneziaWG 250 Мбит, а тут 30».** Реальные
202 Мбит через Hysteria2 — тот же порядок, что WireGuard, разрыв около 20%,

пакеты в user space, Hysteria — обычный процесс, где логика QUIC (окна,
повторы, congestion control) выполняется в Go на каждый пакет.

Условия замера, чтобы результат был воспроизводим: `hhh-ams-01` **одноядерный**
(`nproc=1`), раздача — `python3 ThreadingHTTPServer`, на время замера с ноды
сняты лишние тестовые инстансы (оставались 4 hysteria + xray).

### 1.2.19 ВАЖНО: salamander и masquerade взаимоисключающи

Обнаружено при проверке боевого профиля 15.08.2026. `[измерено]`

| Профиль | HTTP/3-запрос на порт | Что видит зондирующий |
|---|---|---|
| с salamander (порт 47821) | **код 000**, 0 байт | молчание |
| без salamander (порт 47822) | **код 200**, 15801 байт | `<title>Debian -- The Universal Operating System</title>` |

Причина механическая: salamander XOR-обфусцирует каждый пакет, поэтому
валидный QUIC-хендшейк от обычного клиента до сервера не доходит вовсе —
а маскарад отвечает только на дошедшие запросы. **При включённой
обфускации masquerade никогда не сработает**, сколько его ни настраивай.

Это не баг, а следствие устройства, но нигде не проговорено: в документации
оба механизма описаны как независимые опции.

**Практическая развилка, которую надо выбрать осознанно:**

- **salamander** — на проводе бесструктурный UDP. Пассивный фингерпринтинг
  QUIC не срабатывает. Активное зондирование получает молчание.
- **masquerade** — на проводе опознаваемый QUIC (то есть HTTP/3). Пассивный
  анализ видит QUIC, зато активное зондирование получает живой сайт и
  сервер выглядит обычным веб-хостом.

Что известно из наших же замеров: **QUIC как класс на этих каналах не
режут** — он проходит и к чистым площадкам, и (на уровне хендшейка) к
заблокированным. Значит опознаваемость QUIC сегодня не стоит дорого, а
защита от активного зондирования — реальная ценность.

### 1.2.22 РАБОЧИЕ КОНФИГИ Xray: проверены прокачкой трафика

Подобрано перебором, каждый вариант проверен фактом прокачки, а не тем, что
инбаунд «поднялся». 15.08.2026. `[измерено]`

**Инбаунд (сервер, для config profile панели):**

```json
{
  "tag": "hy2-salamander",
  "listen": "0.0.0.0",
  "port": 47821,
  "protocol": "hysteria",
  "settings": {
    "version": 2,
    "clients": [{ "auth": "ПАРОЛЬ", "email": "user@node" }]
  },
  "streamSettings": {
    "network": "hysteria",
    "security": "tls",
    "tlsSettings": {
      "alpn": ["h3"],
      "certificates": [{
        "certificateFile": "/etc/hysteria/cert.pem",
        "keyFile": "/etc/hysteria/key.pem"
      }]
    },
    "hysteriaSettings": { "version": 2 },
    "finalMask": { "salamander": { "password": "ПАРОЛЬ_ОБФУСКАЦИИ" } }
  }
}
```

**Outbound (клиент):**

```json
{
  "protocol": "hysteria",
  "settings": {
    "version": 2,
    "address": "hhh-sto-01.vpn.cosmdandy.dev",
    "port": 47821
  },
  "streamSettings": {
    "network": "hysteria",
    "security": "tls",
    "tlsSettings": { "alpn": ["h3"], "serverName": "hhh-sto-01.vpn.cosmdandy.dev" },
    "hysteriaSettings": { "version": 2, "auth": "ПАРОЛЬ" },
    "finalMask": { "salamander": { "password": "ПАРОЛЬ_ОБФУСКАЦИИ" } }
  }
}
```

**Четыре правила, каждое стоило отдельного захода:**

1. **`alpn: ["h3"]` обязателен** в `tlsSettings` инбаунда. Без него клиент
   падает с `CRYPTO_ERROR 0x178: tls: no application protocol`, при том что
   порт слушает и сервер выглядит рабочим.
2. **`auth` у клиента лежит в `hysteriaSettings`, а не в `settings`.** Если
   положить в `settings` — соединение устанавливается, но обрывается с
   `transport/internet/hysteria: auth failed`.
3. **Адрес у клиента — в `settings.address/port`.** Структура
   `settings.servers[]` **роняет Xray с segfault**:
   `panic: nil pointer dereference` в `conf.(*HysteriaClientConfig).Build`.
   Это прямой риск для панели: такой конфиг в config profile убьёт Xray на
   ноде вместе с боевыми Reality-инбаундами.
4. **Обфускация: `finalMask.salamander`** на обеих сторонах. Варианты
   `finalMask.udp.salamander` отвергаются парсером.

**Замеры на равных условиях (стенд → `hhh-sto-01`, 26 МБ через
Cloudflare):** `[измерено]`

### 2.2 Механизм

По замерам участников ntc.party. `[измерено]`

Два наблюдаемых паттерна (ValdikSS, 06.08):

1. **Full-drop** — не ходят TCP/UDP/ICMP из РФ; сервер при этом достаёт до
   РФ, но ответы не проходят. Реализовано stateful-файрволлом по ICMP ID.
2. **Мягкий** — UDP не работает, TCP-хендшейк проходит, но ответа после
   первого пакета с данными нет; ICMP работает в обе стороны.

Существенные наблюдения:

- Гранулярность не «весь адрес»: у одного участника забанен `22/tcp`, а `443`
  с vless-xhttp-reality работал. У другого — один адрес из /24 под баном,
  соседний с идентичным конфигом нет.
- Объём трафика не защищает: под бан попадали и 3–5 ТБ/мес, и личные
  500 ГБ–1 ТБ/мес.
- Каскад из двух хопов не спасает — банится входной адрес (оспорено одним
  участником, консенсуса нет).
- Смена IP помогала не всем: у proxyline новые адреса отваливались за сутки.
- Троттлинга «обрыв после N КБ» в этой волне не наблюдалось — это отдельный,
  более ранний слой.

Контраргумент к «крупнейшей в истории»: 0ka измерил, что из 34 адресов с
«vpn» в домене, заблокированных на его скане 26 июня, к 6 августа заблокировано
**только 11**, причём на разблокированных ничего не менялось. `[измерено]`
